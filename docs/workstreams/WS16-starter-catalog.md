# WS16: Starter catalog

**Wave:** 3 · **Suggested model:** Sonnet · **Branch:** `ws/16-starter-catalog`

## Goal
A new household has no recipes until it imports some, so onboarding's calibration deck and the first drafted week would be empty. When this is done, every environment (local, CI, hosted) carries a starter catalog of at least 60 original dinner recipes written for this app, stored with `visibility = 'catalog'` and `source_type = 'ai'`, parsed against the ingredient ontology, and tagged so the `suggest` function and the calibration deck can use them on day one. The recipes live in the repo as reviewable JSON, and Miguel reviews the content before it loads into the hosted project. Decided 2026-10-30 (docs/09, Product).

## In scope
- A one-time drafting script that asks `claude-sonnet-5-5` for original dinner recipes from a coverage spec, validates each against `NormalizedRecipe`, parses every ingredient line with the parser (grammar and ontology lookup; the Haiku fallback is allowed), and writes one JSON file per recipe. The script is resumable (it skips slugs that already exist) and stops at a dollar cap.
- The coverage spec and the tag vocabulary, as code with tests.
- A loader that renders `supabase/seed/20_catalog.sql` from the JSON: idempotent upserts of `recipes` and `recipe_ingredients` with deterministic ids, `household_id null`, `visibility 'catalog'`, `source_type 'ai'`, `source_url null`, `created_by null`, `embedding null`.
- Tests on the JSON and the SQL (below).
- One CI step that proves the catalog loaded after `supabase db reset` and that the SQL is idempotent.
- A review sheet for Miguel: a table of every recipe with title, cuisine, protein, total minutes, diet tags, allergens present, and every ingredient line that did not resolve.
- A section in `supabase/seed/README.md` on the catalog and on loading it into the hosted project.

## Interfaces
**Implements**
- JSON file shape (one recipe):
  ```
  {
    "id": "<uuid v5 of slug under CATALOG_NAMESPACE>",
    "slug": "sheet-pan-lemon-chicken-thighs",
    "title": "...", "description": "...",
    "servings": 4, "prepMin": 10, "cookMin": 25, "cuisine": "...",
    "tags": ["dinner", "chicken", "sheet_pan", "gluten_free", "dairy_free", "kid_friendly"],
    "ingredients": [
      { "position": 0, "groupName": null, "rawText": "8 bone-in chicken thighs", "qty": 8, "qtyMax": null,
        "unit": "each", "ingredientName": "chicken thigh", "ingredientId": "<uuid v5 of the name>",
        "prepNote": null, "optional": false, "parseConfidence": 0.97 }
    ],
    "instructions": ["...", "..."],
    "draft": { "model": "claude-sonnet-5-5", "promptVersion": "catalog-draft.v1", "draftedAt": "2026-10-30T...Z", "costUsd": 0.0123 }
  }
  ```
- `CATALOG_NAMESPACE`, a fixed UUID in `spec.ts`. Recipe id is UUID v5 of the slug. Line id is UUID v5 of `<slug>#<position>`. Never change the namespace; a changed slug is a new recipe.
- `ingredientId` is the ontology's deterministic id (UUID v5 of `ingredientName` under `INGREDIENT_NAMESPACE` from `supabase/seed/load.ts`), so the SQL needs no database to render.
- Tag vocabulary (every tag comes from this list; a test enforces it):
  - course: `dinner` on every recipe
  - protein, exactly one: `chicken`, `beef`, `pork`, `lamb`, `turkey`, `fish`, `shellfish`, `tofu`, `tempeh`, `beans`, `lentils`, `eggs`, `cheese`, `vegetables`
  - diet, only when the deterministic check agrees: `vegetarian`, `vegan`, `gluten_free`, `dairy_free`
  - method, zero or more: `sheet_pan`, `one_pot`, `skillet`, `slow_cooker`, `pressure_cooker`, `grill`, `no_cook`, `bake`
  - audience and pantry, zero or more: `kid_friendly`, `pantry`, `leftovers`, `freezer_friendly`
- Coverage spec, minimums over the whole catalog (a test enforces each line):
  - at least 60 recipes; every one is a dinner main; no title repeats
  - at least 10 distinct cuisines; no cuisine above 12 recipes
  - protein caps: `chicken` 14, `beef` 8, `pork` 6, `lamb` 3, `turkey` 4, `fish` 6, `shellfish` 4; at least 20 with a non-meat protein tag (`tofu`, `tempeh`, `beans`, `lentils`, `eggs`, `cheese`, `vegetables`)
  - at least 20 `vegetarian`, of which at least 8 `vegan`; at least 15 `gluten_free`; at least 15 `dairy_free`
  - at least 30 recipes contain none of the nine allergens (`peanut`, `tree_nut`, `milk`, `egg`, `wheat`, `soy`, `fish`, `shellfish`, `sesame`)
  - at least 40 with `prepMin + cookMin <= 35`; none above 120
  - `servings` is 4 everywhere (the planner scales per household)
  - 5 to 16 ingredient lines per recipe; 4 to 12 instruction steps
  - at least 90 percent of all ingredient lines carry an `ingredientId` with `parseConfidence >= 0.8`
  - at least 15 `kid_friendly`; at least 10 `pantry`
- The deterministic diet and allergen checks in `spec.ts` work from `ingredientName`, the ontology `category` (meat, seafood, dairy, eggs) and short term lists on `rawText`. They decide the diet tags and the allergen column in the review sheet. Keep them conservative: when in doubt the recipe does not get the diet tag.

## Acceptance criteria
1. `node supabase/seed/catalog/load.ts --check` exits 0, and `supabase/seed/20_catalog.sql` and `supabase/seed/catalog/README.md` match the JSON byte for byte.
2. `pnpm test` runs `catalog.test.ts`, which asserts every line of the coverage spec, the tag vocabulary, `NormalizedRecipe` and `RecipeInstructions` validity, `RECIPE_LIMITS`, deterministic ids (recomputed from slug and names), that every `ingredientId` exists in the ontology seed, that diet tags agree with the deterministic check, and that no text contains an em dash, a retailer name (Kroger, QFC, Fred Meyer, Safeway, Albertsons, Costco, Instacart, Walmart, Amazon, Whole Foods, Trader Joe's), a brand name from the banned list in `spec.ts`, a URL, or the words "copycat", "famous", or a chef's or publication's name.
3. In CI, after `supabase db reset`, the step "Catalog seed is loaded" shows `select count(*) from public.recipes where visibility = 'catalog' and deleted_at is null` at 60 or more, `recipe_ingredients` for those recipes at 300 or more, and resolved lines (`ingredient_id is not null`) at 90 percent or more of their lines.
4. The same CI step runs `psql -f supabase/seed/20_catalog.sql` a second time and the three counts do not change.
5. Every catalog row has `household_id null`, `visibility 'catalog'`, `source_type 'ai'`, `source_url null`, `created_by null`, `servings 4`, `embedding null` (asserted in the CI step with one query that returns 0 rows violating any of them).
6. The drafting script, run with `--count 2 --max-usd 0.25` into a temp directory, writes two valid JSON files and prints the cost; run again, it skips both and spends nothing. Paste that output. The full run's total cost and the number of drafts rejected by validation appear in the README.
7. The review sheet lists every recipe with title, cuisine, protein tag, total minutes, diet tags, allergens present, and a final table of every unresolved ingredient line with its recipe.
8. `pnpm typecheck && pnpm lint && pnpm test` pass at the repo root. `pnpm eval` still passes (the catalog must not change parser or import evals).

## Risks and notes
- R5, copyright. The catalog holds only our own recipes. Draft from the spec (cuisine, protein, method, time), never from a named source, a URL or any third-party text. Generic dish names ("chicken tikka masala") are fine; "copycat", publication names, chef names and brand names are not. Instructions are written fresh by the model from the spec. No web fetching anywhere in the script.
- Allergen safety (docs/05). Tags are not the enforcement; WS06's filters match ingredient terms and ontology categories in SQL and again in TypeScript. The catalog helps by resolving ingredient ids and by naming hidden allergens as their own lines: soy sauce, tamari, fish sauce, oyster sauce, Worcestershire sauce (anchovy), miso, sesame oil, tahini, and nut butters each get a `rawText` line. Never bury an ingredient in an instruction step. No "seasoning blend" or "your favorite sauce" without listing what is in it.
- WS06 compatibility. Its diet rules treat these recipe tags as conflicts: `chicken`, `beef`, `pork`, `lamb`, `turkey`, `bacon`, `ham`, `sausage`, `seafood`, `fish`, `shrimp`, `salmon`, `shellfish`, `dairy`, `cheese`, `egg`, `eggs`, `honey`, `contains gluten`. Tag the protein honestly so those rules work. A recipe tagged `dessert`, `drink`, `breakfast` or `snack` is never a dinner candidate, so no catalog recipe carries one. Tags are stored lowercase.
- Units. `unit` holds a canonical code from `packages/core/src/units.ts`; the parser returns it. Write `rawText` in US customary measures ("1 1/2 cups", "2 tbsp", "1 lb").
- Determinism. Ids derive from slugs and ingredient names under fixed namespaces so the same recipe has the same id in local, CI and hosted databases. Changing a slug retires nothing; it creates a second recipe, so pick slugs once.
- The SQL loads after `10_ingredients.sql` (name order). It must upsert by id and must not delete rows, so a hosted re-run after edits updates text in place.
- Cost. Sixty recipes on Sonnet should cost between one and three dollars. `--max-usd` is a hard stop. The key comes from `.env.local` into the process environment only; the script refuses to run when `CI` is set.
- The script writes an `ai_runs` row only when given a database; by default it logs cost to stdout and into each JSON's `draft` block.
- Prose style for every recipe text: short sentences, no em dashes, no filler, no exclamation marks.
